## Clarifications

### Session 2026-10-22

- Q: Как UI должен трактовать пустые числовые поля `limit` и `allow_missing` при отправке формы? → A: Пустые значения трактуются как дефолты V1 (`limit=10`, `allow_missing=0`); пробельный ввод считается пустым; нечисловые значения — ошибка; десятичные значения для `limit`/`allow_missing` — ошибка.
- Q: Как UI должен трактовать и сериализовать checkbox `use_substitutions` при отправке формы? → A: Отсутствие поля означает `false`, присутствие поля означает `true` (семантика стандартной формы); UI НЕ отправляет явное `false` — отсутствие поля является единственным способом передать `false`.
- Q: Как UI должен трактовать `max_cost` при пустом значении и как интерпретировать формат чисел (точка/запятая), отрицательные и нечисловые значения? → A: Пустое значение трактуется как «не задано» и поле не отправляется; допускаются только числа с точкой как десятичным разделителем; отрицательные и нечисловые значения — ошибка.
- Q: Какие визуальные состояния и HTTP‑статусы должна возвращать страница для успешной отправки, ошибок валидации и внутренних ошибок сервера, и нужен ли отдельный индикатор загрузки? → A: Успех и ошибки валидации возвращают 200 и рендерятся на той же странице (результаты или сообщения об ошибках рядом с полями, значения полей сохраняются); внутренние ошибки возвращают 500 с простой страницей ошибки; отдельный индикатор загрузки не используется.
- Q: Как UI должен трактовать и сериализовать поле `diet_tags` при пустом значении, разделителях и дубликатах? → A: Пустое/пробельное значение трактуется как пустой список; UI отправляет пустую строку, сервер парсит в `[]`. Для непустого значения: разделитель — запятая, элементы триммятся, пустые токены отбрасываются, регистр на UI не меняется, дубликаты допускаются на UI (ядро дедуплицирует).

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Ввод pantry и получение планов (Priority: P1)

Пользователь вводит список ингредиентов pantry через форму и получает список подходящих рецептов согласно V1/V2 контракту, с сохранением введённых значений и отображением результатов на той же странице.

**Why this priority**: Это основная ценность UI — предоставить пользователю быстрый ответ на основе имеющихся ингредиентов.

**Independent Test**: При вводе валидного pantry и нажатии Submit пользователь видит результаты, упорядоченные согласно правилам (V0 по имени, при включении расширений — по score), limit применяется.

**Acceptance Scenarios**:

1. **Given** форма открыта, **When** пользователь вводит pantry и нажимает Submit, **Then** страница перерисовывается с результатами и сохранёнными полями формы.
2. **Given** расширения не заданы, **When** отправлен валидный pantry, **Then** результаты отсортированы по имени (ASC) и ограничены `limit`.

---

### User Story 2 - Ошибки валидции полей (Priority: P1)

Пользователь получает понятные сообщения об ошибках рядом с соответствующими полями при неверном вводе, при этом введённые значения сохраняются.

**Why this priority**: Улучшает UX, предотвращает потерю данных и соответствует требованиям V1.

**Independent Test**: При неверном типе `limit` или пустом `pantry` UI остаётся на странице формы, показывает сообщения об ошибках, сохраняет введённые значения.

**Acceptance Scenarios**:

1. **Given** пустой pantry, **When** Submit, **Then** рядом с полем pantry сообщение об ошибке; остальные поля сохраняют значения.
2. **Given** `limit="0"`, **When** Submit, **Then** сообщение об ошибке у limit; значения других полей не теряются.

---

### User Story 3 - Нет совпадений (Priority: P2)

При отсутствии подходящих рецептов пользователь видит понятное сообщение, а форма сохраняет введённые значения.

**Why this priority**: Предотвращает фрустрацию и подтверждает, что запрос обработан.

**Independent Test**: При pantry без совпадений отображается сообщение "Нет подходящих рецептов", форма сохраняет значения, раздел результатов пуст.

**Acceptance Scenarios**:

1. **Given** валидный pantry без совпадений, **When** Submit, **Then** отображается сообщение об отсутствии совпадений и пустой список результатов.

---

### Edge Cases

- Большое число ингредиентов в pantry: форма и отображение остаются пригодными к использованию.
- Повторяющиеся ингредиенты в pantry: нормализация и дедупликация на стороне ядра; UI не вмешивается.
- Ввод pantry через много строк и через запятые: оба способа поддерживаются.
- Пустые числовые поля `limit`/`allow_missing`: трактуются как дефолты V1; десятичные значения для целочисленных полей → ошибка; пробельный ввод считается пустым.
- Checkbox `use_substitutions`: незаконченный — параметр отсутствует (false); отмеченный — параметр присутствует (true).
- Поле `max_cost`: пустое → поле не отправляется; десятичный разделитель — точка; запятая/нечисловое → ошибка; отрицательные значения → ошибка.
- Состояния и статусы: успех и ошибки валидации — 200 на той же странице (результаты или полевые сообщения); внутренняя ошибка — 500 с простой страницей ошибки; отдельного индикатора загрузки нет (серверный рендер).
- Поле `diet_tags`: пустое/пробельное → пустой список; разделитель — запятая; элементы триммятся; пустые токены отбрасываются; регистр сохраняется; дубликаты допускаются на UI (ядро дедуплицирует).

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: UI MUST предоставлять форму с полями:
  - `pantry` — textarea; ввод через запятые или по строкам; обязательное поле.
  - `limit` — текстовое числовое поле; по умолчанию 10.
  - `allow_missing` — текстовое числовое поле; по умолчанию 0.
  - `diet_tags` — текстовое поле; ввод через запятые; по умолчанию пусто.
  - `max_cost` — текстовое числовое поле; пустое значение означает отсутствие ограничения.
  - `use_substitutions` — checkbox; по умолчанию выключен.
- **FR-002**: Параметры формы SHALL соответствовать параметрам API V1 по именам и смыслу. Преобразование типов выполняется на сервере.
- **FR-003**: UI MUST отправлять данные на `POST /` и отображать результаты на той же странице (`GET /` отображает форму).
- **FR-004**: UI MUST отображать каждый рецепт: `name`, `score`, `cost`, `tags`, `ingredients`, `missing`, `used_substitutions` с возможностью раскрытия деталей через `<details>`.
- **FR-005**: При отсутствии совпадений UI SHALL отображать понятное сообщение и пустой список результатов.
- **FR-006**: UI MUST отображать сообщения об ошибках рядом с полями, включая: пустой/неверный `pantry`, некорректные `limit`, `allow_missing`, `diet_tags`, `max_cost`, `use_substitutions`.
- **FR-007**: UI MUST сохранять введённые значения в полях при ошибках и при отображении результатов.
- **FR-008**: UI MUST использовать общее ядро планирования и валидации; UI SHALL NOT вычислять `score`, сортировку или `limit` самостоятельно.
- **FR-009**: Сортировка, `score` и применение `limit` SHALL соответствовать ответу API/ядра; UI отображает в полученном порядке без переупорядочивания.
- **FR-010**: Значения по умолчанию в форме SHALL соответствовать V1: `limit=10`, `allow_missing=0`, `diet_tags=[]`, `max_cost` пусто (нет ограничения), `use_substitutions=false`.
- **FR-011**: Пустые числовые поля `limit` и `allow_missing` SHALL трактоваться как «не заданы» и маппиться на дефолты V1; пробельный ввод считается пустым. Нечисловой ввод MUST считаться ошибкой; десятичные значения для `limit`/`allow_missing` MUST считаться ошибкой.
- **FR-012**: Параметр `use_substitutions` SHALL следовать семантике checkbox: отсутствие поля → `false`, присутствие поля → `true`. UI SHALL NOT отправлять явное `false`; отсутствие поля является единственным способом передать `false`.
- **FR-013**: Поле `max_cost` SHALL интерпретироваться так: пустое значение → поле не отправляется (нет ограничения); допускаются только числа с точкой как десятичным разделителем; отрицательные и нечисловые значения MUST считаться ошибкой.
- **FR-015**: Статусы и состояния страницы SHALL быть следующими: успешный запрос и ошибки валидации возвращают 200 и рендерятся на той же странице (результаты или сообщения об ошибках рядом с полями при сохранении значений); внутренние ошибки MUST возвращать 500 с простой страницей ошибки; отдельный индикатор загрузки SHALL отсутствовать.
- **FR-014**: Поле `diet_tags` SHALL трактоваться так: пустая/пробельная строка → пустой список; разделитель — запятая; элементы MUST быть обрезаны по краям; пустые токены SHALL отбрасываться; регистр SHALL сохраняться на UI; дубликаты допускаются на UI (ядро выполняет дедупликацию и нормализацию).

### Key Entities

- **PantryInput**: текстовое представление pantry (строки и/или CSV), преобразуется в список строк на сервере.
- **PlanResult**: список рецептов с полями `name`, `ingredients`, `missing`, `used_substitutions`, `tags`, `cost`, `score`.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 95% валидных запросов показывают результаты за < 1 секунду после отправки формы.
- **SC-002**: 100% ошибок валидации отображаются рядом с соответствующими полями без потери введённых значений.
- **SC-003**: В 100% случаев порядок рецептов в UI совпадает с порядком из ядра/API.
- **SC-004**: 100% пустых ответов отображают понятное сообщение без ошибок и с сохранением полей.

## Assumptions

- В проекте уже есть общее ядро планирования и валидации, переиспользуемое UI.
- UI работает в одном окне/странице: `GET /` (форма) и `POST /` (обработка и та же страница).
- Сообщения об ошибках и поля локализованы на русский, термины и имена полей оставлены на английском.
