# Pantry Planner Agent


## Назначение
- Агент подбирает блюда по списку доступных ингредиентов (pantry).
- Возвращаются только те рецепты, которые можно приготовить строго по имеющимся ингредиентам (без докупки).

## Стек
- Python 3.10+
- Flask (минимальный backend, REST API)
- pytest (юнит- и API-тесты)

## API
- POST /v1/plan:
  - Вход:
    {
      "pantry": ["egg", "milk", "salt"],
      "limit": 5
    }
    pantry — обязательный список строк; limit — опционально (>=1), по умолчанию 10.
  - Ответ 200:
    {
      "recipes": [
        {"name": "Omelet", "ingredients": ["egg", "milk", "salt"]}
      ]
    }
  - Ошибки 400:
    - отсутствует поле pantry
    - pantry не список
    - pantry пустой
    - элементы pantry не строки
    - limit < 1 или некорректного типа

## Данные
- recipes.json: список простых рецептов вида
  {"name": "Omelet", "ingredients": ["egg", "milk", "salt"]}

## Алгоритм 
- Нормализация ингредиентов: регистронезависимое сравнение, обрезка пробелов.
- Рецепт включается в результат, если все его ингредиенты содержатся в pantry.
- Результаты сортируются по имени рецепта для детерминизма.
- Применяется ограничение limit.

## Планируемые расширения

Разделы выше описывают V0. Далее — изменения для будущих V1 и V2.

### Фича 1 (V1): гибкое планирование

- Сохранить `POST /v1/plan`, добавив опциональные параметры: `allow_missing` — целое >= 0 (по умолчанию 0), `diet_tags` — список строк (по умолчанию []), `max_cost` — число >= 0 (по умолчанию без ограничения), `use_substitutions` — bool (по умолчанию false). Некорректный ввод возвращает 400.
- В `recipes.json` добавить `tags` и `cost`; при отсутствии использовать `[]` и `0.0`. Рецепты должны содержать хотя бы один непустой ингредиент.
- Добавить рядом `substitutions.json` вида `{"scallion": ["green onion"]}`: ключ — ингредиент рецепта, значения — допустимые замены в pantry. Отсутствующий файл означает отсутствие замен.
- Сохранить нормализацию через `strip().lower()`. Повторения ингредиентов не учитывать. Замены включаются только флагом, работают в одном направлении и за один шаг; прямое совпадение имеет приоритет.
- Допускать рецепт, если число недостающих ингредиентов <= `allow_missing`, присутствуют все запрошенные теги и стоимость <= `max_cost`, когда он задан.
- Рассчитывать `score = covered_count / total - 0.5 * missing_count / total - 0.1 * min(cost, 10) / 10`, где `total` — число уникальных нормализованных ингредиентов рецепта.
- При значениях новых параметров по умолчанию сохранять строгий отбор и сортировку V0 по имени. При включении любого расширения сортировать по score по убыванию, затем по имени по возрастанию. `limit` применять последним.
- Всегда дополнять записи ответа полями `missing`, `used_substitutions`, `tags`, `cost`, `score`, сохраняя `name` и `ingredients`. `missing` — нормализованные недостающие ингредиенты; замены — строки вида `"scallion<-green onion"`. Пустой результат — `{"recipes": []}`.

### Фича 2 (V2): минимальный UI

- Добавить `GET /` с формой и `POST /` с результатами на той же странице. Использовать Flask + Jinja2, шаблоны в `src/templates/`.
- Поля формы: pantry, limit, allow_missing, diet_tags, max_cost и checkbox use_substitutions. Pantry вводится через запятые или по строкам, теги — через запятые; числовые поля преобразуются на сервере. Значения по умолчанию соответствуют V1, пустой max_cost означает отсутствие ограничения.
- API и UI используют общий вызов планирования и валидацию. UI сохраняет полученный порядок и limit; контракт API V1 не меняется.
- Показывать название, score, стоимость, теги, состав рецепта, недостающие ингредиенты и применённые замены. Missing визуально выделять, детали можно раскрывать через HTML `<details>`.
- При ошибках показывать сообщения рядом с полями, сохраняя введённые значения; возвращать HTML со статусом 200. При отсутствии совпадений показывать понятное сообщение.
