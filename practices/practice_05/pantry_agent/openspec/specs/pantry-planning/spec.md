# pantry-planning Specification

## Purpose
Гибкое планирование рецептов по списку pantry с допуском недостающих ингредиентов, фильтрацией по диет-тегам, ограничением стоимости, одношаговыми подстановками и ранжированием по score. Поведение V0 сохраняется при значениях по умолчанию.

## Requirements

### Requirement: POST /v1/plan поддерживает параметры V1
Система SHALL принимать JSON с полями: `pantry` (list[str]), `limit` (int ≥ 1, по умолчанию 10), `allow_missing` (int ≥ 0, по умолчанию 0), `diet_tags` (list[str], по умолчанию []), `max_cost` (number ≥ 0 или отсутствует), `use_substitutions` (bool, по умолчанию false).

#### Scenario: Валидный запрос с дефолтами
- **WHEN** клиент отправляет pantry=["egg","milk","salt"] без дополнительных параметров
- **THEN** ответ 200 с `recipes`, строгий отбор V0, сортировка по имени

### Requirement: Расширенный контракт ответа
Система SHALL возвращать для каждого рецепта: `name`, `ingredients`, `missing` (нормализованные недостающие), `used_substitutions` (строки вида `recipe<-pantry`), `tags` (список), `cost` (число), `score` (округлено до 3 знаков). Пустой результат SHALL быть `{ "recipes": [] }`.

#### Scenario: Пустой результат
- **WHEN** ни один рецепт не удовлетворяет условиям
- **THEN** ответ 200 с телом `{ "recipes": [] }`

### Requirement: Нормализация и уникальность
Система SHALL нормализовать ингредиенты и теги через `strip().lower()` и игнорировать дубли ингредиентов в рецепте при расчётах.

#### Scenario: Нормализация регистр/пробелы
- **WHEN** pantry и рецепт содержат разные регистры/пробелы
- **THEN** сравнение выполняется по нормализованным значениям

### Requirement: Правила допуска рецепта
Система SHALL включать рецепт, если `missing_count ≤ allow_missing`, рецепт содержит все теги из `diet_tags`, а при заданном `max_cost` выполняется `cost ≤ max_cost`.

#### Scenario: Фильтр по тегам (AND)
- **WHEN** diet_tags=["vegetarian","breakfast"]
- **THEN** включаются только рецепты, содержащие оба тега

### Requirement: Подстановки ингредиентов (одношаговые)
Система SHALL поддерживать substitutions.json при `use_substitutions=true`. Подстановка одношаговая и односторонняя: ключ — ингредиент рецепта, значения — допустимые замены из pantry. Прямое совпадение имеет приоритет. При множественных валидных заменах выбирается первая по порядку. Отсутствующий файл означает отсутствие замен.

#### Scenario: Успешная подстановка
- **WHEN** рецепт требует `scallion`, pantry содержит `green onion`, substitutions {"scallion":["green onion"]}, `use_substitutions=true`
- **THEN** рецепт допущен; `used_substitutions` содержит `"scallion<-green onion"`

#### Scenario: Прямое совпадение сильнее
- **WHEN** pantry содержит `scallion` и `green onion`
- **THEN** подстановка не используется; `used_substitutions` пуст

### Requirement: Данные рецептов и валидация
Система SHALL читать recipes.json, допуская дефолты `tags=[]` и `cost=0.0`. Каждый рецепт MUST иметь ≥1 непустой ингредиент. Неверные типы или `cost < 0` SHALL приводить к ошибке загрузки.

#### Scenario: Некорректные данные
- **WHEN** рецепт имеет пустые ингредиенты или отрицательную стоимость
- **THEN** загрузка данных завершается ошибкой

### Requirement: Score и сортировка
Система SHALL рассчитывать `score = covered/total - 0.5 * missing/total - 0.1 * min(cost,10)/10`, где `total` — число уникальных ингредиентов рецепта; `score` округляется до 3 знаков. При дефолтных параметрах сортировка SHALL быть по имени (ASC). При включении любого расширения сортировка SHALL быть по score (DESC), затем по имени (ASC). `limit` применяется последним.

#### Scenario: Сортировка по имени в режиме V0
- **WHEN** расширения не заданы
- **THEN** порядок идентичен V0 (по имени)

#### Scenario: Сортировка по score при расширениях
- **WHEN** `allow_missing>0` или `diet_tags` не пуст или задан `max_cost` или `use_substitutions=true`
- **THEN** сортировка по score убыв., затем по имени

### Requirement: Ошибки валидации входа
Система SHALL возвращать 400 для: отсутствует `pantry`/не список/пустой/содержит не строки; `limit` не int ≥ 1; `allow_missing` не int ≥ 0; `diet_tags` не список строк; `max_cost` не число ≥ 0; `use_substitutions` не bool.

#### Scenario: 400 при неверных новых полях
- **WHEN** одно из новых полей нарушает ограничения
- **THEN** ответ 400
