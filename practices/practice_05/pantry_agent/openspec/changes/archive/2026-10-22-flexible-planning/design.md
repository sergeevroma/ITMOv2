# Design

## Context
- Текущее API: POST /v1/plan, строгий отбор V0, сортировка по имени, limit.
- Источник рецептов: `src/data/recipes.json`.
- Требования V1: allow_missing, diet_tags, max_cost, use_substitutions; расширение данных (tags, cost); substitutions.json; score; изменяемая сортировка; совместимость V0 по умолчанию.

## Goals / Non-Goals

**Goals:**
- Добавить гибкие параметры без нарушения V0 по умолчанию.
- Детерминированная сортировка и стабильный контракт ответа.
- Строгая валидация входов и данных рецептов.

**Non-Goals:**
- UI (V2 вне рамок).
- Многошаговые/двунаправленные подстановки.

## Decisions

1) Нормализация тегов
- Нормализуем теги `strip().lower()` (согласовано).

2) Округление score
- Округляем до 3 знаков при формировании ответа.

3) Валидация recipes.json
- Ошибка загрузки при отрицательной `cost`, пустых ингредиентах, неверных типах.

4) Подстановки
- Прямое совпадение имеет приоритет; при множественных матчах выбор первой из списка; одношаговость.

5) Переключатель сортировки
- Включение расширений: `allow_missing>0` или `diet_tags` не пусты или задан `max_cost` или `use_substitutions=true`.

## Risks / Trade-offs
- [Округления score] → Округление до 3 знаков; вторичный ключ — имя.
- [Сложность валидации] → Явная проверка типов и диапазонов; покрыть тестами.
- [Производительность] → Для объёма учебного проекта достаточно; используем множества и уникализацию ингредиентов.

## Migration Plan
- Последовательное внедрение: ядро планирования, API-валидация, расширение данных, тесты, проверка совместимости V0.
- Rollback: вернуть V0-логику; дополнительные поля ответа могут быть проигнорированы старыми клиентами.
