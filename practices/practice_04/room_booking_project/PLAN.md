## 2. Фича A: запрет пересечений

- При создании бронирования сервис проверяет расписание той же комнаты
на ту же дату. Если время пересекается с существующей записью, возвращается HTTP 409 с понятной причиной и ID конфликтующего бронирования. Новая запись при отказе не сохраняется.

- Интервалы считаются полуоткрытыми: `[start, end)`. Поэтому встречи
10:00–11:00 и 11:00–12:00 могут идти подряд. Условие пересечения:

```text
new_start < existing_end AND existing_start < new_end
```

- Проверки для приёмки A:

  - Частичное пересечение, вложенный интервал и полный дубль дают 409.
  - После отказа состав базы не меняется.
  - Соседние интервалы разрешены.
  - Одинаковое время в разных комнатах или в разные даты разрешено.
  - Создание корректных записей, чтение и удаление продолжают работать.

- Агент применяет TDD: сначала тест на отсутствующую проверку, его фактическое падение, затем реализация и успешный запуск всей проверки проекта.

- После просмотра diff и результатов A принимается и сохраняется в commit
вместе с настройками среды.

## 3. Styleguide и hook: только после A

- После приёмки A агент читает готовый код и тесты, предлагает 3–5 правил, нужных этому проекту, и сохраняет `docs/style-guide.md` с хорошим примером. Ссылка на этот файл добавляется в `AGENTS.md`, перед реализацией фичи B агент явно его читает.

- Затем добавляется Ruff линтер с настройками, соответствующими выбранным проверяемым правилам. Поведение сервиса по-прежнему проверяет pytest. Теперь `scripts/check.sh` запускает тесты и Ruff, возвращает ненулевой код при сбое. 

- Сначала `scripts/check.sh` проверяется вручную, затем подключается hook проверки.

### Что делает hook

Плагин `.opencode/plugins/check-after-edit.js` запускает один фиксированный `sh scripts/check.sh` после изменения Python-файлов инструментами агента `edit`, `write` или `apply_patch`. По мере появления Python-кода skill и MCP он также включается в проверки.

- Команда запускается из каталога проекта текущего worktree.
- Агент получает PASS или FAIL, код завершения и вывод проверок в результате инструмента. Записи в отдельный лог или уведомления недостаточно.
- Hook не исправляет код автоматически и не меняет файлы проверки.
- Проверки выполняются последовательно, с тайм-аутом 30 секунд;
  истечение тайм-аута считается сбоем.

### Демонстрация работы hook

Агент вносит временное нарушение одного из реально проверяемых
правил, получает автоматический FAIL, исправляет его и получает PASS.
Временное нарушение не входит в принятую версию проекта.

## 4. Фича B: поиск свободного времени

- После сохранения A, styleguide и hook создаётся отдельный Git worktree для ветки B. В нём запускается новый чат агента с актуальными правилами.

- Добавляется endpoint:

```text
GET /free-slots?date=YYYY-MM-DD&duration_minutes=60&room_id=101
```

  1. дата и длительность обязательны; комната необязательна. Без комнаты поиск выполняется по всем трём комнатам. Длительность — положительное целое число, кратное 30, не больше 540 минут. Ошибочный вход возвращает 422.

  2. cервис перебирает возможные начала с шагом 30 минут в пределах 09:00–18:00 и возвращает все подходящие интервалы: `room_id`, `date`, `start`, `end`.

  3. результат сортируется по началу и комнате. Соседние варианты могут
перекрываться между собой, если они испрользуют разные комнаты

  4. Поиск использует общие правила пересечения из A и не изменяет базу. Если вариантов нет, возвращается пустой список.

- Проверки для приёмки B:

  - Каждый вариант имеет запрошенную длительность и укладывается в рабочий день.
  - Ни один вариант не пересекается с сохранёнными бронированиями.
  - Поиск по одной комнате и по всем комнатам даёт ожидаемые результаты.
  - Проверяются пустое расписание, полностью занятый день и ошибочный вход.
  - Все тесты A остаются успешными; поиск не меняет записи.


## 5. Что делают skills

### Готовый skill: test-driven-development

- В первой части практики используется
[test-driven-development](https://github.com/obra/superpowers/tree/main/skills/test-driven-development)
вместе с его reference `writing-good-tests.md`. Пакет сохраняется локально
в `.opencode/skills/test-driven-development/` со связанными ресурсами.

- Skill задаёт процедуру разработки A и B: проверить контракт, написать тест,
увидеть ожидаемое падение, реализовать минимальное изменение, выполнить
проверки и при необходимости сделать рефакторинг.

- Подтверждение применения: вызов загрузки skill, чтение reference,
вывод падающего и проходящего теста, реальный diff.

### Собственный skill: booking-csv-audit

- В домашке создаётся пакет `.opencode/skills/booking-csv-audit/`:
`SKILL.md`, Python-скрипт, описание формата CSV и примеры входных файлов с заранее известными результатами.

- Назначение: проверить пакет заявок на бронирование до их внесения в расписание.
Формат CSV: `room_id,title,date,start,end`.

- Скрипт:

  1. Читает CSV, проверяет заголовки, поля, комнаты и допустимость времени.
  2. Получает существующие бронирования через API проекта.
  3. Находит пересечения внутри CSV и с существующим расписанием,
    используя общую логику интервалов приложения.
  4. Создаёт JSON и Markdown-отчёт: число заявок, номера строк,
    причины ошибок и конфликтующие строки или ID бронирований.

- Отчёт отмечает обе стороны конфликта внутри CSV. Ни одна заявка не импортируется
автоматически. Если расписание недоступно, скрипт возвращает ошибку и не выдаёт
частичный аудит за успешно завершённую проверку.


- **Содержательная автоматизация находится в скрипте** проверка данных,
сопоставление с расписанием и расчёт конфликтов.
Результат сверяется с ожидаемым отчётом для подготовленного примера,
а сохранённые бронирования остаются прежними.

## 6. Что делают MCP

### Context7: документация для первой части практики

- [Context7](https://github.com/upstash/context7) подключается как удалённый MCP
по адресу `https://mcp.context7.com/mcp` через конфигурацию OpenCode, при необходимости настраивается API-ключ сервиса.

- Конкретная задача для A: найти в документации FastAPI способ вернуть
HTTP 409 при конфликте и проверить статус и JSON ответа через TestClient.

- На демонстрации агент вызывает `resolve-library-id`, затем `query-docs`: показываются вход инструментов, ответ с документацией и найденные источники, а затем применение найденного подхода в реализации и тесте A.


### Собственный MCP: поиск свободных интервалов

- В домашке создаётся локальный Python MCP-сервер со stdio-транспортом
и одним инструментом:

```text
find_free_slots(date, duration_minutes, room_id=None)
```

- Tool обращается к API фичи B и возвращает список подходящих интервалов.

- Ошибочный вход возвращает понятную ошибку MCP tool, недоступность API — отдельную ошибку.

- Пример поручения агенту: «Найди свободную комнату на час 2099-10-12».
На защите показываются реальный успешный вызов, ошибочный вызов
с `duration_minutes=0` и сверка результата с API.

5. Поручить ИИ создать styleguide по готовой A; добавить Ruff и hook.
   Показать автоматические FAIL и PASS, сохранить настройки.

7. Проверить объединённое состояние, создать `docs/HANDOFF.md` и показать, что новая сессия понимает состояние и запускает проверку.
8. В домашке создать и проверить `booking-csv-audit` и собственный MCP.
9. Написать `reflection.md` с конкретными наблюдениями
