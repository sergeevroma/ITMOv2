# Разработка RoomBook

## Установка и запуск

Команды выполняются из корня проекта RoomBook. Нужен Python 3.11+.

```sh
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.lock
.venv/bin/python -m uvicorn roombook.main:create_app --factory --reload
```

Документация API: `http://127.0.0.1:8000/docs`, контракт: `/openapi.json`.
SQLite создаётся при запуске приложения в `data/roombook.sqlite3`.
Путь можно переопределить переменной `ROOMBOOK_DB`; относительный путь считается
от текущего рабочего каталога.

`requirements.lock` фиксирует проверенный набор зависимостей и устанавливает
проект в editable-режиме. Исходные зависимости объявлены в `pyproject.toml`.

## Проверка

Один раз установите Chromium для клиентских тестов в каталог окружения:

```sh
PLAYWRIGHT_BROWSERS_PATH="$PWD/.venv/playwright-browsers" .venv/bin/python -m playwright install chromium --only-shell
```

Затем запустите все проверки:

```sh
sh scripts/check.sh
```

Команда запускает Ruff, проверку форматирования, актуальности OpenAPI и тесты
бэкенда и клиента. Тесты API используют TestClient и временные базы, включая
проверку восьми одновременных попыток занять один интервал.
Клиентские тесты в `tests/client/` используют pytest + Playwright: подменяют
ответы API, проверяют форму, создание, отмену, повторные действия, состояния и клавиатуру.
Полный сценарий с настоящим API проверяется отдельно с временной SQLite-базой и сервером
на свободном локальном порту; пользовательская база и запущенный сервер не используются.
Скрипт сам задаёт `PLAYWRIGHT_BROWSERS_PATH` для установленного Chromium.

## Устройство

| Файл в `src/roombook/` | Ответственность |
|---|---|
| `catalog.py` | Фиксированный каталог комнат и оборудования |
| `rules.py` | Рабочее время, шаг, форматы даты и времени, пересечение интервалов |
| `schemas.py` | Входные и выходные модели; проверка данных при создании брони |
| `service.py` | Работа с бронированиями, проверка комнаты, подбор свободного времени |
| `repository.py` | Хранение, сортировка, транзакции SQLite |
| `api.py` | Маршруты и преобразование запросов в вызовы сервиса |
| `main.py` | Фабрика приложения, инициализация хранилища, ответы с ошибками, статика |

## Начальная страница

После запуска FastAPI откройте `http://127.0.0.1:8000/`.
Начальный экран выполнен по макету `design/main.png`. Комнаты, правила выбора
времени и расписание загружаются из API. По умолчанию выбрана сегодняшняя дата
в часовом поясе из правил; смена даты и фильтра комнаты перечитывает список.
При быстром переключении предыдущий запрос отменяется. Загрузка, пустой ответ
и ошибка с возможностью повтора имеют отдельные состояния.
Примерных записей в HTML нет. Создание и отмена работают через POST и DELETE.
Во время создания форма и дата заблокированы; при отмене блокируется кнопка брони.
Ошибки сохраняют заполненную форму, успех обновляет расписание.

```text
src/front/
├── index.html
├── styles.css
├── app.js
└── vendor/
    ├── bootstrap.min.css
    └── bootstrap.LICENSE.txt
```

`index.html` задаёт структуру и использует готовые компоненты Bootstrap 5.3.9.
В начале `styles.css` находятся общие переменные цветов, шрифта, размеров текста,
отступов и фокуса. Ниже — оформление компонентов и адаптивная раскладка:
на широком экране две колонки, при ширине менее 992 CSS-пикселей — одна.
Рабочая область ограничена по ширине, страница прокручивается по вертикали.

Bootstrap подключён локально, внешних шрифтов и CDN нет. Для текущих карточек,
полей, кнопок и обычных `<select>` достаточно CSS библиотеки; её JavaScript
потребуется, только если появятся компоненты вроде модального окна.
Сборщик и Node.js для запуска страницы не нужны.

`app.js` делает относительные запросы `fetch('/api/...')` и заполняет HTML-шаблоны
комнат и бронирований. Тексты из ответов выводятся через `textContent`.
Браузер и API работают на одном
адресе, а SQLite остаётся локальным файлом, с которым работает только Python.
В браузере не нужно открывать файл базы или создавать отдельное хранилище.

## Хранение и правила

Для каждой операции открывается отдельное соединение с SQLite. Создание брони
выполняется через `BEGIN IMMEDIATE`: проверка пересечений и вставка входят
в одну транзакцию. Каталог комнат задаётся в коде как данные.

Время хранится как местное `HH:MM`, дата — `YYYY-MM-DD`, зона — `Europe/Moscow`.
Сервис не запрещает работу с прошедшими датами и не учитывает праздники.
Пересечение: `new_start < saved_end` и `saved_start < new_end`.
Свободные интервалы — все подходящие варианты с шагом 30 минут; варианты
могут пересекаться между собой и не являются заранее созданными бронями.
Сохранение всегда повторно проверяет занятость.

## Контракт для фронтенда

Машиночитаемый источник — [openapi.json](openapi.json), он генерируется из приложения.

| Метод и путь | Назначение |
|---|---|
| `GET /api/rooms` | Каталог с вместимостью и оборудованием |
| `GET /api/booking-rules` | Рабочее время, шаг выбора, часовой пояс |
| `GET /api/bookings?date=2027-03-15` | Расписание; необязательный фильтр `room_id` |
| `POST /api/bookings` | Создать бронь: `room_id`, `organizer`, `title`, `date`, `start`, `end` |
| `DELETE /api/bookings/{booking_id}` | Отменить бронь |
| `GET /api/free-slots?date=2027-03-15&duration_minutes=60` | Подобрать время; фильтр `room_id` необязателен |

Списки возвращаются обычными JSON-массивами; отсутствие записей — `[]`.
Бронирование содержит переданные поля и серверный `id`. Расписание сортируется
по комнате, началу и ID; свободные интервалы — по началу и комнате.
Название ограничено 120 символами, имя организатора — 80, пробелы по краям удаляются.

Ошибки валидации (422), пересечения (409) и отсутствующей брони (404) имеют форму:

```json
{
  "error": {
    "code": "validation_error",
    "message": "Проверьте введённые данные.",
    "fields": {"title": "Поле не должно быть пустым."}
  }
}
```

Коды: `validation_error`, `booking_conflict`, `booking_not_found`.
`fields` — словарь ошибок полей, иногда пустой; `_form` означает ошибку формы целиком.
Неизвестные маршруты, сетевые и неожиданные серверные ошибки клиент обрабатывает
общим сообщением с возможностью повторить действие.

Чтобы обновить сохранённый контракт после изменения API:

```sh
.venv/bin/python scripts/export_openapi.py
```

## Артефакты для работы над интерфейсом

Сейчас готовы описание области, инструкции агенту, техническая инструкция и контракт.
Для одного экрана достаточно следующей последовательности:

1. **Макет** в `design/`: исходник или ссылка и доступный экспорт кадров.
   Показывает расположение элементов, подписи, пустые данные, ввод, загрузку,
   результат, ошибку; также нужен вариант для узкого экрана.
   Отдельно фиксируется, что предложил AI и что изменено после проверки.
2. **`docs/frontend-spec.md`** после согласования макета: основной сценарий,
   поля и ограничения, таблица состояний, действия при ошибках, клавиатурная
   навигация, адаптивность и проверяемые условия готовности.
   Для каждого действия указываются реальный запрос и ожидаемый видимый результат.
   В конце — небольшой список задач с отметками выполнения.
3. **Интерфейс и браузерные тесты** по макету и спецификации. Тесты подменяют API
   в соответствии с контрактом, проверяют видимые результаты и ровно один запрос
   при повторной отправке во время ожидания.
4. **Свидетельства проверки** в `evidence/`: скриншоты, вывод всех клиентских тестов,
   примеры AI-запросов и описание исправлений. Они добавляются после реальных запусков.

Макеты уже находятся в `design/`, основной сценарий описан в `README.md`.
Готовый интерфейс находится в `src/front/`; поведение зафиксировано
в `docs/frontend-spec.md`, скриншоты и вывод тестов — в `evidence/`.
Чтобы обновить скриншоты при запуске клиентских тестов:

```sh
PLAYWRIGHT_BROWSERS_PATH="$PWD/.venv/playwright-browsers" .venv/bin/python -m pytest tests/client -q --evidence-dir=evidence/screenshots
```

Без `--evidence-dir` тесты не перезаписывают сохранённые свидетельства.

Проверить, что тест обнаруживает скрытое сообщение об ошибке:

```sh
.venv/bin/python scripts/check_error_test.py
```

Скрипт ломает только временную копию фронтенда и ожидает падение одного теста
на видимости сообщения; рабочие файлы не меняются. Успешный контроль завершится с кодом 0.
В начале нового чата достаточно передать `AGENTS.md`
и конкретную задачу. После появления макета к ним добавляются его экспорт
и спецификация интерфейса. Новые решения следует записывать в соответствующий
документ, чтобы следующий агент получил тот же контекст.

Фронтенд размещается в `src/front/`. Если каталог существует,
FastAPI отдаёт его как статику с `/`, а API остаётся под `/api`.
Так клиент сможет выполнять относительные запросы `fetch('/api/...')`.
HTML-прототип макета, если он используется, хранится отдельно в `design/`.
