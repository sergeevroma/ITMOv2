## Разбор zero-shot 

- **Принял** — наблюдение LLM обосновано показанным кодом и имеющимся контекстом

    - app/api.py — No size limits or guards for the incoming diff: в представленном коде действительно нет явной проверки размера diff до формирования запроса.

    - Раздел Open questions: вопросы о недостающем контексте


- **Отклонил** — основание считать это ошибкой недостаточно

    - app/api.py — Path naming inconsistency: правило маршрутизации не предоставлено, отрицательное последствие не доказано.LLM превратила предпочтение по организации API в серьёзный дефект.

    - app/review_service.py — Response shape is underspecified: Модель видит ответ {"comment": answer}, но не получила требования к его структуре. Поэтому она не может установить, что одного комментария недостаточно.

    - app/api.py — No authentication/authorization: неизвестны условия доступа и требования к защите. Оставить как вопрос о недостающем контексте можно, утверждать отсутствие защиты у всего сервиса нельзя.

    - app/review_service — Style nit: стилистическое предпочтение без установленного правила и доказанного последствия.

- **Исправил бы** — полезное замечание, но формулировка преувеличена или содержит ошибку

    - app/api.py — Missing request validation: замечание принято частично. Код обращается к payload["diff"] без явной проверки наличия ключа. Однако утверждение о возврате HTTP 500 не доказано: обработка исключений может находиться вне показанного diff. Кроме того, неправильный тип значения сам по себе не вызывает KeyError — эта ошибка возникает при отсутствии ключа.

    - app/api.py — Unspecified/loose OpenAPI schema: частично повторяет Missing request validataion, явная модель запроса одновременно улучшает проверку входа и документацию API

## Master Prompt v1

Соберите здесь контракт второго запуска. Не копируйте все документы целиком — ставьте ссылки на файлы и переносите только необходимый для задачи контекст.

### 1. Цель и роль

- Роль AI: ревьюер кода и аналитик учебного кейса. 
- Цель: За один запуск подготовь доказательное ревью `TRAINING_PR.diff` с подготовленным Context Pack, сохрани результат в `results/P1-02.md` и создай согласованную модель возможного проекта AI Reviewer, заполнив 11 связанных SDLC артефактов

### 2. Входы и источники

- Рабочая папка: `practices/practice_01` относительно корня репозитория. Все пути указаны относительно этой папки.
- Обязательный входы: `TRAINING_PR.diff` и раздел «Context Pack для первого рабочего сценария» в `context.md`. Прочитай Context Pack полностью: он определяет природу кейса, правила, входы, результаты и ограничения.
- Разрешённые файлы и источники: перечислены в разделе «Формат входа и результата» Context Pack. Прочитай их с диска на соответствующем этапе работы.
- Изначальные SDLC артефакты задают структуру документов. Сохранённый P1-01 и его разбор используются для последующего сравнения, а факты о реализации устанавливаются по diff.


### 3. Задача и артефакты

- Создай `results/P1-02.md` с самостоятельным ревью по контракту Context Pack.
- Заполни разрешённые разделы всех 11 перечисленных Markdown-файлов в соответствии с их назначением и шаблонами.
- В `context.md` заполни таблицу «Продукт и команда сейчас» и раздел «Как использовали AI», сохранив подготовленный Context Pack
- В `prompts.md` заполни строку P1-02, раздел «Разбор master prompt» и таблицу сравнения. Укажи ссылки на ревью, заполненный раздел разбора «Разбор master prompt»
- Заполни разделы «Как использовали AI» тем же запуском. Отдели выполненную самопроверку AI от ожидающей проверки человеком.

### 4. Формат результата

- Для `P1-02.md` используй JSON-контракт из раздела «Формат входа и результата» Context Pack; помести JSON в блок кода внутри Markdown-файла.
- Записывай документы непосредственно в файлы на русском языке, сохраняя заголовки, таблицы и предусмотренные шаблонами диаграммы и сценарии.
- Ограничения объёма: краткие содержательные формулировки, одна согласованная модель проекта, детализация только для обоснования решений и воспроизведения проверок.
- Финальное сообщение: изменённые файлы, итоги статической самопроверки и оставшиеся вопросы для человека.

### 5. Полномочия и запреты

- Соблюдай раздел «Ограничения и запрещённые действия» Context Pack целиком.
- Используй инструменты чтения и редактирования только в установленной области. Проверки этого запуска ограничены статическим анализом документов и diff.
- Защищённые «материалы P1-01» включают оба файла первого запуска, строку P1-01 и раздел «Разбор zero-shot» в prompts.md.
- AS IS основывай на источниках; недостающие факты обозначай как неизвестные. Проблему, целевые метрики и будущие решения формулируй как обоснованные учебные гипотезы или предложения.

### 6. Рабочий процесс и остановка

1. Прочитай `context.md` и `TRAINING_PR.diff`. Определи применимые правила и границы доступной информации.

2. Подготовь самостоятельное ревью. Проверь доказательства, номера строк целевых файлов, последствия рисков и воспроизводимость проверок. Сохрани результат в `results/P1-02.md` до чтения `P1-01.md` и `prompts.md`.

3. Прочитай остальные шаблоны. Определи защищённые разделы и перечень полей, которые требуется заполнить.

4. Последовательно подготовь связанную учебную модель:

    - `context.md` и `problem.md`: известное состояние, пользовательская проблема, предлагаемые метрики и способы измерения;

    - `analysis.md` и `product_management.md`: AS IS, предлагаемый TO BE, пользовательский сценарий и критерии приёмки; соблюдай требования шаблона к нотации;

    - `adr.md`: решение со статусом proposed, альтернативы, последствия и архитектурная схема;

    - `project_management.md`: инкременты, роли и зависимости, соответствующие выбранному решению; сроки обозначь как условный учебный план;

    - четыре `tests_*.md`: проекты проверок этого же решения. Для нагрузки используй предусмотренное шаблоном обоснование, если требований недостаточно.

5. Прочитай материалы первого запуска. Сравни их с сохранённым `P1-02.md` по четырём критериям таблицы в `prompts.md`, приводя конкретные примеры. Отрази как улучшения, так и недостатки второго ответа. Сохрани исходный `P1-02.md`: обнаруженные на этом этапе ошибки запиши в разборе.

6. Заполни журнал и разделы «Как использовали AI». Оценки обозначь как предварительный разбор AI. Модель укажи по подтверждённым данным сессии; при отсутствии данных оставь явную пометку для пользователя. Отрази условия запуска, включая доступ к чтению и редактированию файлов.

7. Перечитай полученные документы, проверь их согласованность и исправь разрешённые проектные разделы. Заверши работу после выполнения Definition of Done.

### 7. Проверки и evidence

- Для каждого риска сверь наблюдение с diff и применимым правилом. Номера строк считай по новой версии целевого файла.

- Проверь цепочку: проблема → требование → процесс и сценарий → архитектура → планируемая проверка. Проектные документы должны учитывать все применимые правила, даже если в ревью выбраны только три риска.

- Для неизвестных метрик укажи способ измерения; для предложенных значений — основание. Сохраняй смысл требований: например, REL-1 ограничивает внешний LLM-вызов.

- В тестовых артефактах разделяй ожидаемый результат и полученное evidence. Для невыполненных тестов укажи статус и доказательство, которое потребуется сохранить.

- В журнале сохрани ссылки, конкретные результаты статической самопроверки и её ограничения. Отдельно проверь ссылки между документами и сохранность защищённых разделов.

### 8. Definition of Done

- Задача закончена, когда:

    - самостоятельное ревью сохранено в `results/P1-02.md` и соответствует контракту Context Pack;

    - разрешённые разделы всех 11 артефактов заполнены: содержательно либо с объяснением неизвестного или неприменимости;

    - документы описывают одну согласованную учебную модель, а предложения отделены от фактов и результатов выполнения;

    - строка P1-02, разбор, сравнение и разделы использования AI содержат ссылки и честную оценку выполненной работы;

    - защищённое содержимое сохранено;

    - финальное сообщение содержит результат работы и вопросы, оставшиеся для человека.

## Сравнение двух запусков

| Проверка | Zero-shot | С master prompt | Вывод команды |
|---|---|---|---|
| Есть ссылка на файл или строку | Частично: файлы/диапазоны указаны, но без явного номера строки | Есть file и точная line по новой версии | Улучшение: повышена точность адресации |
| Вывод подтверждён diff или правилом | Смешано: есть предположения (например, путь префиксов) | Связка evidence+правило в каждом риске | Улучшение: доказательность выросла |
| Соблюдены границы AI | В целом да | Да, дополнительно зафиксировано в артефактах | Без изменений |
| Есть воспроизводимая проверка | Рекомендации без формальных шагов | Чёткие Given/When/Then в checks и тестах | Улучшение: появилась воспроизводимость |
