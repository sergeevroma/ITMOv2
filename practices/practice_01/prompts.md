## Разбор zero-shot 

- **Принял** — наблюдение LLM обосновано показанным кодом и имеющимся контекстом

    - app/api.py — No size limits or guards for the incoming diff: в представленном коде действительно нет явной проверки размера diff до формирования запроса.

    - Раздел Open questions: вопросы о недостающем контексте


- **Отклонил** — основание считать это ошибкой недостаточно

    - app/api.py — Path naming inconsistency: правило маршрутизации не предоставлено, отрицательное последствие не доказано.LLM превратила предпочтение по организации API в серьёзный дефект.

    - app/review_service.py — Response shape is underspecified: Модель видит ответ {"comment": answer}, но не получила требования к его структуре. Поэтому она не может установить, что одного комментария недостаточно.

    - app/api.py — No authentication/authorization: неизвестны условия доступа и требования к защите. Оставить как вопрос о недостающем контексте можно, утверждать отсутствие защиты у всего сервиса нельзя.

    - app/review_service — Style nit: стилистическое предпочтение без установленного правила и доказанного последствия.

- **Исправил бы** — полезное замечание, но формулировка преувеличена или содержит ошибку

    - app/api.py — Missing request validation: замечание принято частично. Код обращается к payload["diff"] без явной проверки наличия ключа. Однако утверждение о возврате HTTP 500 не доказано: обработка исключений может находиться вне показанного diff. Кроме того, неправильный тип значения сам по себе не вызывает KeyError — эта ошибка возникает при отсутствии ключа.

    - app/api.py — Unspecified/loose OpenAPI schema: частично повторяет Missing request validataion, явная модель запроса одновременно улучшает проверку входа и документацию API

## Master Prompt v1

Соберите здесь контракт второго запуска. Не копируйте все документы целиком — ставьте ссылки на файлы и переносите только необходимый для задачи контекст.

### 1. Цель и роль

- Цель: за один запуск выполнить повторное ревью `TRAINING_PR.diff` и заполнить 11 связанных markdown файлов практики 1 для учебного AI-помощника ревьюера. Сохранить полученный ревью и сопоставь его с сохранённым zero-shot ревью `P1-01`.

- Роль AI: инженер, который анализирует предоставленный код, готовит проектную документацию и проверяет согласованность своих выводов.


### 2. Входы и источники

- Рабочая папка — `practices/practice_01` относительно корня форка. Все короткие пути ниже относятся к этой папке.

- Разрешённые файлы и источники: `TRAINING_PR.diff`, `context.md`, `prompts.md`, `results/P1-01.md`, `results/zero_shot_prompt.md` и шаблоны `problem.md`, `analysis.md`, `product_management.md`, `project_management.md`, `adr.md`, `tests_unit.md`, `tests_integration.md`, `tests_load.md`, `tests_e2e.md`.

- Context Pack — прочитай весь раздел «Context Pack для первого рабочего сценария» в `context.md` до выполнения ревью. Его факты, правила, формат, примеры и ограничения являются частью этой инструкции. Сохрани этот раздел без изменений.

- `CASE.md` и `README.md` использованы при подготовке инструкции. Дополнительно читать их, остальной репозиторий и внешние источники для выполнения этого запуска не требуется и не разрешено.

### 3. Задача и артефакты

- Подготовь самостоятельное ревью предоставленного diff по правилам Context Pack. Сохрани результат ревью в `results/P1-02.md` как JSON в блоке кода по формату OUT-1. Ограничения анализа укажи отдельным текстом рядом. Не воспроизводи весь чат или скрытые рассуждения.

- Заполни содержательные разделы всех перечисленных 11 документов: `context.md`, `problem.md`, `analysis.md`, `product_management.md`, `project_management.md`, `adr.md`, `tests_unit.md`, `tests_integration.md`,`tests_load.md`, `tests_e2e.md`, `prompts.md`  Существующие заголовки, таблицы и требуемые блоки диаграмм/сценариев сохрани, заменяя заглушки осмысленным содержанием. Исключения — защищённые части, перечисленные в разделе 5.

- Тем же запуском заполни разделы «Как использовали AI» во всех документах, включая тестовые:
   - «Для чего» — конкретная задача AI для данного документа.
   - «Тип промпта» — `master prompt`.
   - «Строка в prompts.md» — `[P1-02](prompts.md#p1-02)`; добавь при этом якорь `<a id="p1-02"></a>` перед таблицей журнала, не меняя строку `P1-01`.
   - «Что проверили и исправили сами» — реально выполненная самопроверка с пометкой «Самопроверка AI».Если исправления не понадобились, так и напиши.


### 4. Формат результата

- Структура ответа: результат ревью соответствует `OUT-1`, документы пиши по-русски, кратко и конкретно; код, идентификаторы правил сохраняй без перевода. В финальном сообщении перечисли изменённые файлы, краткие итоги самопроверки и оставшиеся неизвестные сведения. Не утверждай, что приложение, тесты или Make-команды запускались.

- Полностью заполни разрешённые разделы файлов на диске. Одного плана заполнения или текста «остальное без изменений» недостаточно.

- Используй относительные ссылки между документами. В записи `P1-02` укажи ссылку на `[Master Prompt v1](#master-prompt-v1)` и на `[Результат P1-02](results/P1-02.md)`. Длинный разбор второго запуска размести отдельным подразделом журнала и сошлись на него из ячеек таблицы. Не добавляй внутри строки Markdown-таблицы физические переносы; при необходимости используй `<br>`.


### 5. Полномочия и запреты

- Разрешено: читать перечисленные входы, редактировать перечисленные 11 Markdown-файлов и создать `results/P1-02.md`.

- Сохрани без изменений раздел Context Pack в `context.md`, весь Master Prompt v1, строку `P1-01` и раздел «Разбор zero-shot» в `prompts.md`, а также содержимое `results/P1-01.md` и `results/zero_shot_prompt.md`.

- Запрещено: все разделы и таблицы peer review оставь для другого человека. Не генерируй замечания ревьюера от его имени. Пустая резервная строка `P1-03` не означает необходимость третьего запуска — сохрани её. 

- Не изменяй Python-код, `TRAINING_PR.diff`, Makefile, конфигурацию и остальные файлы. Не выполняй shell-команды, web-запросы, git commit/push, approve или merge. Проверки Make пользователь выполнит отдельно.

- Не выдумывай источники, измеренные метрики, сведения о команде, результаты тестов, модель сессии или действия человека. Сведения, которых нет во входах, обозначай как неизвестные, а предлагаемые решения и цели — как предложения.

### 6. Рабочий процесс и остановка

- Шаги:
    1. Убедись, что обязательные входы доступны; прочитай шаблоны и Context Pack. Определи защищённые разделы перед редактированием.
    2. Выполни ревью diff по переданным правилам; для каждого кандидата проверь evidence. Приоритет отдай обоснованным рискам безопасности, нарушения контракта и надёжности. Сохрани `results/P1-02.md`.
    3. Подготовь документы в порядке: контекст и проблема → процесс и сценарии → план и архитектура → проверки. Свяжи проблему, цели, правила, решения и проверки ссылками или идентификаторами.
    4. Сопоставь собственное ревью с фактическим `P1-01`; не переписывай первый ответ. Отметь конкретные улучшения, оставшиеся недостатки и случаи, когда второй ответ не лучше. Учти, что первый запуск не получал правил, поэтому отсутствие ссылки на неизвестное ему правило не является само по себе выдумкой модели.
    5. Заполни журнал и разделы использования AI. Проведи статическую самопроверку содержимого и ссылок, затем исправь обнаруженные несогласованности в разрешённых частях.
    6. Заверши работу после выполнения Definition of Done

- Когда остановиться и запросить человека: Если обязательный файл недоступен или входы противоречат друг другу так, что продолжение требует выдумать факт

### 7. Проверки и evidence

- Как проверять утверждения: 
    - для утверждения о нарушении укажи наблюдаемое поведение и соответствующее требование
    - отсутствие кода в фрагменте не доказывает отсутствие проверки во всей системе
    - выводы о скрытом клиенте LLM и глобальных обработчиках обозначай как неизвестные.

- Какое evidence сохранить:
    - для каждого риска — путь файла, номер строки новой версии, точную цитату из diff и применимое правило.
    - для каждой предложенной проверки — вход, действие и ожидаемый результат.
    - в тестовых документах — способ получить подтверждение; если тест не запускался, явно написать «не выполнено».
    - в сравнении запусков — конкретные примеры из ответов P1-01 и P1-02, подтверждающие оценку.

### 8. Definition of Done

- Задача закончена, когда:
    - Все 11 документов содержательно заполнены в разрешённых разделах одним выполнением этого master prompt; соответствующие требования и проверки согласованы.
    - `results/P1-02.md` содержит доказанное ревью
    - В `prompts.md` заполнены запись `P1-02` и все четыре строки сравнения; есть ссылки на результаты и собственная критическая оценка AI.
    - Разделы «Как использовали AI» заполнены честно, допущения и неизвестные сведения обозначены, результаты невыполненных тестов не придуманы.
    - Context Pack, Master Prompt v1, baseline и разбор пользователя сохранены; peer review и резервная строка `P1-03` не заполнены; посторонние файлы не изменены.
    - В итоговом ответе названы результаты статической самопроверки и проверки, которые остаётся выполнить человеку.
